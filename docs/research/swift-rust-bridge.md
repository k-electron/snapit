# Swift ↔ Rust bridge and shipping both in one app

Research for [#2](https://github.com/k-electron/snapit/issues/2), part of the map [#1](https://github.com/k-electron/snapit/issues/1).
Researched 2026-11-19. Sources are primary (official docs, the projects' own repos, changelogs, source code, crates.io API). Every claim links to where it comes from.

## Question

Which Swift↔Rust bridge should snapit use (UniFFI, swift-bridge, or a hand-written C ABI with cbindgen), and how is the Rust engine built for arm64 and linked so the app bundle is fully self-contained? Cover Xcode/SwiftPM integration, build-time cost, binary-size impact, Swift 6 strict concurrency, and maintenance health.

## Answer

**Use a small hand-written C ABI, with the header generated by cbindgen, behind a thin Swift wrapper that we write and own. Build the engine as one Rust `staticlib` for `aarch64-apple-darwin` and link it statically into the app executable.** Then the bundle holds one Mach-O binary with no embedded dylibs or frameworks to load or sign. It also has no bridge runtime in it.

Why this fits snapit:

- **The interface is narrow and handles large buffers.** The engine takes pixel buffers in and gives pixel buffers or encoded bytes back. A 6K Retina Capture is about 80 MB of RGBA. A C ABI can pass a borrowed pointer both ways and return Rust-owned bytes to Swift without copying. UniFFI can borrow input without a copy, but returned `Vec<u8>` goes through its serialized `RustBuffer`. Its zero-copy *write-in-place* `&mut [u8]` is still unreleased ([UniFFI CHANGELOG](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md), [bytes docs](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/types/bytes.md)).
- **Swift 6 concurrency stays under our control.** Both generators still have open Swift 6 / Xcode 26 problems (details below). With a C ABI the only Swift we compile is our own wrapper.
- **No runtime dependency.** cbindgen is only a build tool, and its output is our own header. Nothing third-party from the bridge ends up in the binary. With UniFFI, the MPL-2.0 `uniffi_core` crate would ship inside the app ([uniffi/Cargo.toml](https://github.com/mozilla/uniffi-rs/blob/main/uniffi/Cargo.toml)).
- **The cost is a few hundred lines of unsafe glue that we own.** We write the ownership rules, error codes and the Swift wrapper by hand. That stays cheap only while the API stays small. If the engine API grows into many record and enum types, switch to **UniFFI**. It is the best-maintained generator by a wide margin, so it is the fallback.

## Constraints from the map that drive this

From [#1](https://github.com/k-electron/snapit/issues/1): macOS 26+, Apple Silicon only, Rust engine for the image pipeline, Swift owns everything that touches the OS, fully contained in the bundle, 0% idle CPU, low memory, reputable open-source deps only, MIT, DMG not notarized. [#6](https://github.com/k-electron/snapit/issues/6) will benchmark the engine through whatever bridge is chosen here, so the bridge must not add copies of a 6K frame.

## The options

### 1. UniFFI (Mozilla)

How it works: annotate Rust with `#[uniffi::export]` proc-macros, or use a UDL file. Then run `uniffi-bindgen-swift` against the built library to emit three things: a C header, a modulemap, and a `.swift` file with idiomatic classes, structs, enums and `throws` ([Swift overview](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/swift/overview.md), [uniffi-bindgen-swift](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/swift/uniffi-bindgen-swift.md)). It can emit XCFramework-compatible modulemaps ([same](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/swift/uniffi-bindgen-swift.md)).

- **Xcode/SwiftPM**: the manual's Xcode page leaves building the staticlib to you ("beyond the scope of this document"). It describes a build rule that runs `uniffi-bindgen`, plus a bridging header ([xcode.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/swift/xcode.md)). `cargo-swift` wraps this into a Swift package, but it supports UniFFI only up to 0.31.x and must be version-matched by hand ([cargo-swift README](https://github.com/antoniusnaumann/cargo-swift/blob/main/README.md)).
- **Swift 6**: the manual says "UniFFI has partial support for Swift 6". Most generated code is `Sendable`, but "async code will not conform" ([overview.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/swift/overview.md); [#2458](https://github.com/mozilla/uniffi-rs/issues/2458), open). Code generated into a module that uses the Xcode 26 default `MainActor` isolation fails to compile. The reporter's workaround is a `sed` pass that adds `nonisolated` to every declaration ([#2818](https://github.com/mozilla/uniffi-rs/issues/2818), open; a maintainer agreed to an option but nothing has shipped). A Swift 6.2 `Data.bytes` name clash is reported ([#2803](https://github.com/mozilla/uniffi-rs/issues/2803), open; the `init(bytes:)` template is unchanged on main, [RustBufferTemplate.swift](https://github.com/mozilla/uniffi-rs/blob/main/uniffi_bindgen/src/bindings/swift/templates/RustBufferTemplate.swift)). A modulemap problem on Xcode 26/27 is reported too ([#2917](https://github.com/mozilla/uniffi-rs/issues/2917)). A maintainer says Firefox for iOS, which uses UniFFI heavily, builds fine on Xcode 26.5 and 27, so this one is disputed.
- **Large buffers**: as of 0.32.0, `&[u8]` arguments are borrowed zero-copy from Swift `Data` ([CHANGELOG v0.32.0](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md), [bytes.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/types/bytes.md)). They are "argument position only" and "cannot be returned". `&mut [u8]` zero-copy writes exist only in the unreleased section ([CHANGELOG](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md)). Swift-side `RustBuffer` decoding is measured at about 10× slower than the Kotlin bindings ([#3013](https://github.com/mozilla/uniffi-rs/issues/3013), open). That hurts record-heavy calls, not single big buffers.
- **Runtime footprint**: the `uniffi` crate pulls in `uniffi_core` (deps `anyhow`, `async-trait`, `bytes`, `once_cell`, `static_assertions`) and proc-macros ([uniffi/Cargo.toml](https://github.com/mozilla/uniffi-rs/blob/main/uniffi/Cargo.toml), [uniffi_core/Cargo.toml](https://github.com/mozilla/uniffi-rs/blob/main/uniffi_core/Cargo.toml)). The generated Swift runs a checksum check when the library initializes, which can be turned off with `omit_checksums` ([configuration.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/swift/configuration.md)).
- **License**: MPL-2.0 ([crates.io](https://crates.io/crates/uniffi)). MPL code may be statically linked into a larger work under another license. Recipients must be told where the MPL source is ([MPL 2.0 FAQ Q8, Q11](https://www.mozilla.org/en-US/MPL/2.0/FAQ/)). That means one line in the app's notices. It doesn't block anything, but it is an obligation.
- **Stability**: pre-1.0. "Incrementing the minor version here means a breaking change to consumers" ([uniffi/Cargo.toml](https://github.com/mozilla/uniffi-rs/blob/main/uniffi/Cargo.toml)). 0.29, 0.30, 0.31 and 0.32 each listed breaking changes ([CHANGELOG](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md)). A 1.0 FFI is still being designed ([#2155](https://github.com/mozilla/uniffi-rs/issues/2155)).

### 2. swift-bridge

How it works: declare a `#[swift_bridge::bridge] mod ffi { extern "Rust" {…} extern "Swift" {…} }` module. Then `swift-bridge-build` in `build.rs` generates the Swift and C glue. It supports opaque types, transparent structs and enums, `Option`, `Result`, `Vec`, async, and calls in both directions ([README](https://github.com/chinedufn/swift-bridge/blob/master/README.md)).

- **Xcode/SwiftPM**: the book has Xcode+Cargo, swiftc+Cargo and Swift Package chapters ([SUMMARY](https://github.com/chinedufn/swift-bridge/blob/master/book/src/SUMMARY.md)). Its Xcode chapter is an iOS example built on `cargo-lipo` ([xcode-and-cargo](https://github.com/chinedufn/swift-bridge/blob/master/book/src/building/xcode-and-cargo/README.md)). cargo-lipo's own README says "consider this project deprecated / passively maintained" ([cargo-lipo](https://github.com/TimNN/cargo-lipo/blob/master/README.md)).
- **Swift 6**: Swift 6 async support only arrived in 0.1.59 (2026-01-06) ([release notes](https://github.com/chinedufn/swift-bridge/releases/tag/0.1.59)). Following the book with Xcode's MainActor default gives "Nonisolated deinitializer 'deinit' has different actor isolation" in the generated `RustString` ([#350](https://github.com/chinedufn/swift-bridge/issues/350), open). `#[swift_bridge(Sendable)]` doesn't work on transparent structs ([#365](https://github.com/chinedufn/swift-bridge/issues/365), open).
- **Buffers**: 0.1.59 generated malformed Swift for `fn(input: &[u8]) -> Vec<u8>` ([#370](https://github.com/chinedufn/swift-bridge/issues/370)). The fix landed on `master` 2026-09-05 and is not in a release ([compare 0.1.59...master](https://github.com/chinedufn/swift-bridge/compare/0.1.59...master)).
- **License**: Apache-2.0 / MIT ([crates.io](https://crates.io/crates/swift-bridge)).

### 3. Hand-written C ABI + cbindgen (recommended)

How it works: write `#[repr(C)]` types and `#[unsafe(no_mangle)] pub extern "C" fn` entry points. In edition 2024, `no_mangle` must be written as `unsafe(...)` ([edition guide](https://doc.rust-lang.org/edition-guide/rust-2024/unsafe-attributes.html)). cbindgen generates the C header from that Rust source ([cbindgen README](https://github.com/mozilla/cbindgen/blob/main/README.md)) and can add `swift_name` attributes for nicer imported names ([docs.md, "Generating Swift Bindings"](https://github.com/mozilla/cbindgen/blob/main/docs.md)). Swift imports the header through a `module.modulemap`. We then write one small Swift file that wraps it.

- **Xcode/SwiftPM**: the same wiring as the other two, minus a bindgen step (see [Build and link](#build-and-link)). cbindgen can run as a CLI only when the ABI changes, with the header committed. Then a normal build never compiles cbindgen ([README](https://github.com/mozilla/cbindgen/blob/main/README.md): "Using it as a program means people building your software will need it installed").
- **Swift 6**: we write the wrapper, so we choose its isolation. Swift's unsafe pointer types are explicitly **not** `Sendable`, for example `@available(*, unavailable) extension UnsafeMutableRawPointer: Sendable {}` ([UnsafeRawPointer.swift](https://github.com/swiftlang/swift/blob/main/stdlib/public/core/UnsafeRawPointer.swift), [UnsafePointer.swift](https://github.com/swiftlang/swift/blob/main/stdlib/public/core/UnsafePointer.swift)). Each handle type therefore needs either an `@unchecked Sendable` wrapper whose safety we argue once, or must not cross isolation domains. Mark the wrapper `nonisolated`. Isolation is set per module, and code imported from other modules "would be unaffected by the current module's choice of default" ([SE-0466](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0466-control-default-actor-isolation.md)). Run heavy calls off the main actor with `@concurrent` ([SE-0461](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0461-async-function-isolation.md)).
- **Buffers**: full control in both directions. Swift can lend a pointer to pixels it already holds. Rust can write into a Swift-allocated destination. Rust can return a `{ptr, len}` that Swift wraps with `Data(bytesNoCopy:count:deallocator: .custom { … engine_free … })`, which avoids a copy ([Data docs](https://developer.apple.com/documentation/foundation/data/init(bytesnocopy:count:deallocator:))).
- **Panics**: since Rust 1.81, a panic that escapes an `extern "C"` function aborts the process instead of being undefined behavior ([RELEASES.md 1.81.0](https://github.com/rust-lang/rust/blob/master/RELEASES.md), [PR #116088](https://github.com/rust-lang/rust/pull/116088)). The glue should `catch_unwind` at each entry point and return a status code. Otherwise a panic in the engine kills snapit. UniFFI does this for you: panics become a Swift `Error` in throwing functions, and a fatal error in non-throwing ones ([overview.md](https://github.com/mozilla/uniffi-rs/blob/main/docs/manual/src/swift/overview.md)).
- **License**: cbindgen is MPL-2.0 ([crates.io](https://crates.io/crates/cbindgen)), but it is a build tool and doesn't ship in the app. Its `header` option is "Probably a license", so the generated file carries our MIT header ([docs.md](https://github.com/mozilla/cbindgen/blob/main/docs.md)).
- **Caveat**: cbindgen's README says development is "largely adhoc … cbindgen may randomly fail to support some particular situation" ([README](https://github.com/mozilla/cbindgen/blob/main/README.md)). For a plain C surface (structs, enums, functions, pointers) that risk is small, and the header can always be hand-edited.

## Comparison

| | UniFFI | swift-bridge | C ABI + cbindgen |
|---|---|---|---|
| Swift API quality out of the box | Idiomatic classes/enums/`throws` | Good, with `RustString`/`RustVec` wrapper types | Raw C; we write the Swift wrapper |
| Glue we maintain | ~none | ~none | Small, hand-written unsafe code |
| Swift 6 / Xcode 26 MainActor default | Partial; open issues #2458, #2818 | Partial; open #350, #365 | Ours to get right |
| Zero-copy big buffers | In: yes (`&[u8]`, 0.32). Out/in-place: no (unreleased) | `&[u8]` input fix unreleased | Both directions |
| Ships a bridge runtime in the binary | Yes (`uniffi_core`, MPL-2.0) | Yes (`swift-bridge`, MIT/Apache) | No |
| Build-time cost | proc-macros + a bindgen binary built from the same crate | proc-macros + `build.rs` codegen | Rust compile only (cbindgen run on ABI change) |
| Panic → Swift | `Error` if the function throws, else fatal | not checked | We `catch_unwind` → status code |
| Breaking-change churn | 0.x minor bumps are breaking | 0.1.x | We set it |

**Binary size and build time.** This machine has no Rust toolchain, so no numbers were measured here. Treat the next two points as reasoning rather than measurement, and let [#6](https://github.com/k-electron/snapit/issues/6) measure. The bridge's own code is small next to an image pipeline. Size is dominated by the engine and std, and is driven by `[profile.release]` settings: `lto` ("better optimized code … at the cost of longer linking time"), `codegen-units = 1`, `opt-level = "s"/"z"`, `strip`, `panic` ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)). The generator options add proc-macro compilation (UniFFI and swift-bridge both depend on macro crates) and, for UniFFI, building the `uniffi-bindgen-swift` binary with the `cli` feature ([uniffi/Cargo.toml](https://github.com/mozilla/uniffi-rs/blob/main/uniffi/Cargo.toml)). The C ABI path adds neither to a normal build.

## Build and link

1. **Crate type**: `crate-type = ["staticlib", "rlib"]`. A staticlib "contain[s] all of the local crate's code along with all upstream dependencies … including the standard library" ([Rust reference: linkage](https://doc.rust-lang.org/reference/linkage.html)). The `rlib` keeps `cargo test` working. Build **one** staticlib for the whole engine: "Multiple Rust `staticlib` files are likely to conflict" ([same](https://doc.rust-lang.org/reference/linkage.html)). Use `--print=native-static-libs` to list the system libraries to add to the link line ([same](https://doc.rust-lang.org/reference/linkage.html)).
2. **Target**: `aarch64-apple-darwin` is Tier 1 with host tools, macOS 11.0+ ([platform support](https://doc.rust-lang.org/rustc/platform-support.html)). Set `MACOSX_DEPLOYMENT_TARGET=26.0` for cargo so the Rust objects match the app. rustc "respects the common environment variables used by Xcode", and raising the deployment target "might yield more performance optimizations" ([apple-darwin](https://doc.rust-lang.org/rustc/platform-support/apple-darwin.html)). No `lipo` or universal build is needed, since the target is arm64 only.
3. **Header and module**: commit `engine/include/snapit_engine.h`, generated by cbindgen, plus a `module.modulemap` that exposes it as a Clang module (for example `SnapitEngineFFI`). CI regenerates the header and fails on any diff.
4. **Xcode wiring (simplest)**: add a Run Script phase before Compile Sources that runs `cargo build --release --target aarch64-apple-darwin`. Cargo is incremental, so an unchanged engine is a near-no-op. Point `SWIFT_INCLUDE_PATHS` at the include directory, add the target directory to `LIBRARY_SEARCH_PATHS`, and add `-lsnapit_engine` to `OTHER_LDFLAGS`. New projects turn on `ENABLE_USER_SCRIPT_SANDBOXING`, which "disallow[s] undeclared input/output dependencies" ([Xcode build settings](https://developer.apple.com/documentation/xcode/build-settings-reference#User-Script-Sandboxing)). Either declare the crate's inputs and outputs, or turn the setting off for that phase.
   *Alternative*: package the `.a`, header and modulemap as an XCFramework (`xcodebuild -create-xcframework -library … -headers …`, [Apple](https://developer.apple.com/documentation/xcode/creating-a-multi-platform-binary-framework-bundle)). Consume it from a local Swift package `binaryTarget(path:)` ([Apple](https://developer.apple.com/documentation/xcode/distributing-binary-frameworks-as-swift-packages)). This is cleaner for `swift test`, but the XCFramework must exist before package resolution, so a script has to build it first. Repo layout and CI belong to [#5](https://github.com/k-electron/snapit/issues/5).
5. **Self-contained bundle and signing**: static linking puts the engine inside `snapit.app/Contents/MacOS/snapit`. There is no dylib or framework to embed, no `@rpath`, and nothing else to sign. On Apple silicon "any executable must be signed before it's allowed to run … a simple ad-hoc signature is sufficient". The linker adds that signature, but tools that modify a binary after linking (`strip`, `install_name_tool`) "might need … `codesign(1)`" re-run ([macOS 11 Universal Apps release notes](https://developer.apple.com/documentation/macos-release-notes/macos-big-sur-11_0_1-universal-apps-release-notes)). That fits a DMG that is not notarized.
6. **Release profile** (starting point, to be confirmed by measurement in #6): `lto = "fat"` or `"thin"`, `codegen-units = 1`, `strip = "symbols"` ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)). Keep `panic = "unwind"` so `catch_unwind` at the FFI boundary works. `panic = "abort"` would turn every engine panic into a crash ([Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)), and binaries containing unwinding calls must use the unwind strategy throughout ([linkage](https://doc.rust-lang.org/reference/linkage.html)).

## Shape of the ABI (sketch, not a spec)

```rust
#[repr(C)] pub struct SnapPixels { data: *const u8, width: u32, height: u32, bytes_per_row: u32 }
#[repr(C)] pub struct SnapBytes  { ptr: *mut u8, len: usize }        // Rust-owned, freed by snapit_bytes_free
#[repr(C)] pub enum   SnapStatus { Ok = 0, InvalidArgument, Panic, … }

#[unsafe(no_mangle)] pub extern "C" fn snapit_pixelate(src: SnapPixels, dst: *mut u8, rect: SnapRect, block: u32) -> SnapStatus;
#[unsafe(no_mangle)] pub extern "C" fn snapit_encode_png(src: SnapPixels, out: *mut SnapBytes) -> SnapStatus;
#[unsafe(no_mangle)] pub extern "C" fn snapit_bytes_free(b: SnapBytes);
```

Rules: every entry point is synchronous. Rust spawns no threads and no async runtime, which matches 0% idle CPU, and the Swift side decides where work runs. Every entry point wraps its body in `catch_unwind`. Swift owns input pixel memory, and Rust owns returned `SnapBytes` until `snapit_bytes_free`. The Swift wrapper is a `nonisolated` module that exposes `Data`, `CGImage`-friendly values and `throws`.

## Recommendation and trade-offs

**Recommended: hand-written C ABI + cbindgen header, one static Rust library for `aarch64-apple-darwin`, linked into the app executable, wrapped by a small `nonisolated` Swift module we own.**

Gains: zero-copy buffers in both directions. No bridge runtime or MPL obligation in the shipped binary. No dependence on generator fixes for Swift 6 or Xcode 26. Smallest dependency surface for OSV-Scanner and Dependabot. One binary to sign ad-hoc.

Costs: unsafe glue to write and review, including ownership, lifetimes, panic catching and error mapping. No generated idiomatic Swift types. Any rich data that crosses the boundary (for example an Annotation list for compositing) has to be flattened to `#[repr(C)]` arrays by hand. A mistake shows up as a crash or leak rather than a compile error.

Switch to **UniFFI** (pinned version, generated Swift in its own non-MainActor module, `omit_checksums` optional) if the boundary grows past a handful of functions and a couple of plain structs. Avoid **swift-bridge** for now: it has one maintainer, its fixes are unreleased, and its Swift 6 issues are still open.

## Open questions surfaced

- **Where the engine boundary sits** ([#6](https://github.com/k-electron/snapit/issues/6)) decides how much data crosses it. If Annotation compositing moves to Rust, the Annotation model must cross as flat C data, and that is the point where UniFFI's generated records start to pay for themselves.
- **Getting Capture pixels to Rust without a copy**: can the ScreenCaptureKit output (IOSurface/CVPixelBuffer-backed) be locked and lent to Rust directly, and in which pixel format and row stride? That depends on [#3](https://github.com/k-electron/snapit/issues/3). The C ABI should take `bytes_per_row` explicitly either way.
- **Measured numbers**: compile time and binary-size deltas weren't measured here (no Rust toolchain on this machine). [#6](https://github.com/k-electron/snapit/issues/6) should record the engine's release `.a` size, the app binary size, and clean and incremental build times.
- **Whether the engine may use worker threads** (for example a parallel blur). Idle threads use no CPU but do hold stack memory. Decide with [#4](https://github.com/k-electron/snapit/issues/4) and [#6](https://github.com/k-electron/snapit/issues/6).
- **Repo and CI wiring** (Xcode run-script vs local SwiftPM package with XCFramework, a header-drift check, a pinned Rust toolchain via `rust-toolchain.toml`) belongs to [#5](https://github.com/k-electron/snapit/issues/5).
